# R.C.T.F.

**Артефакт Практики 1: `adr.md`**

## 1. Техника и зачем она здесь

RCTF делает промпт и сам текст ADR **структурно явными**: кто пишет, из какого контекста, что решить, в каком формате фиксировать пункты решения — меньше смешения контуров A/B в одной фразе.

## 2. Вход (фрагмент выбранного артефакта)

Раздел «Решение» до ужесточения формата допускал смешение «помощник + API» без правила записи.

## 3. Запрос (четыре блока)

**Role:** архитектор учебной команды; фиксируешь ADR, не патчишь продукт.

**Context:** учебный кейс README + `TRAINING_PR.diff`; два возможных контура (помощник vs код в diff).

**Task:** перепиши «Решение» в `adr.md` нумерованным списком с метками контуров; добавь правило формата записи пункта решения.

**Format:**

```text
N. **Контур X:** … Источник: … | или Открытый вопрос: …
```

Плюс короткий абзац «Формат записи решения».

### Что даёт каждый блок

| Блок | Эффект на результат |
|---|---|
| Role | Нет propose merge/патчей кода |
| Context | Не склеивает чат и FastAPI в один runtime |
| Task | Конкретная правка раздела «Решение» |
| Format | Единообразие пунктов + место для «Открытый вопрос» |

## 4. Фактический результат

В `adr.md` раздел «Решение» — три пункта с контурами A/B/границы; добавлен подраздел «Формат записи решения (зафиксирован few-shot / RCTF)».

## 5. Что приняли / отклонили

- **Приняли:** нумерация с метками контуров.
- **Отклонили:** формулировку «единый прод-пайплайн чат→API».
