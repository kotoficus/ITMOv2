# Research: решения для Spec и Plan

Исследование основано на фактическом проекте, согласованиях в диалоге и
официальном workflow Spec Kit. Это работа одного автора документов;
независимое ревью или исследование отдельными агентами не заявляется.

## R1. Процесс и корень проекта

**Decision:** использовать Spec Kit, корень `practices/practice_05`, текущую
Git-ветку `practice_05` и отдельную feature-directory
`specs/001-complex-expression-calculator`.

**Rationale:** пользователь прямо запросил Spec и Plan Spec Kit; текущий
официальный workflow разделяет feature-directory и Git-ветку. Есть уже
существующий проект с ESM и `node:test`, поэтому новый продукт не нужен.

**Alternatives considered:** продолжить старую проверку чисел через OpenSpec
— не соответствует новому согласованному scope. OpenSpec-черновик остаётся
помеченным как заменённый, без фиктивных apply/приёмки/archive.

## R2. Разбор выражений

**Decision:** отдельный лексер и рекурсивный спуск по уровням приоритета,
результат — AST с диапазонами исходного ввода.

**Rationale:** грамматика мала и фиксирована. Такой парсер прямо отражает
приоритет, унарные знаки и скобки, позволяет сообщить точную позицию ошибки.
Арифметика при разборе не выполняется — это согласовано пользователем.

**Alternatives considered:** shunting-yard с AST тоже подходит, но добавляет
отдельные стеки без выигрыша для этой грамматики; готовая математическая
библиотека приносит лишний язык и зависимость; `eval`/`Function` смешивают
разбор с исполнением и не соответствуют заданному контракту.

## R3. Числовая модель и операции

**Decision:** все новые вычисления используют plain objects `{re, im}` с
конечными компонентами Number. Чистые функции реализуют комплексную
арифметику; вещественные значения не имеют отдельного пути вычисления.

**Rationale:** согласованная модель; объекты напрямую сериализуемы и не
требуют восстановления прототипов при последующем чтении JSON.

**Alternatives considered:** два типа real/complex требуют приведения в
каждой операции; классы не нужны для четырёх функций; arbitrary precision
не запрошена. Обычное округление binary64 сохраняется.

Для деления сначала проверить точный комплексный ноль. Затем взять
`s = max(abs(c), abs(d))`, нормировать делитель `c' = c/s`, `d' = d/s`,
использовать `q = c'² + d'²` и масштабированные компоненты числителя
`a' = a/s`, `b' = b/s`. Компоненты частного:
`(a'c' + b'd')/q` и `(b'c' - a'd')/q`.
Это устраняет безусловный расчёт квадратов больших/малых исходных
компонент делителя. Нечисловые или бесконечные промежуточные значения
и результаты отклоняются с `NUMERIC_OVERFLOW`. Данная стратегия не
обещает точного результата во всём математическом диапазоне чисел:
числовое переполнение остаётся частью контракта.

## R4. Язык и вывод

**Decision:** поддержать десятичные литералы, `i`, коэффициент `2i`,
унарные знаки, четыре операции, скобки и ASCII-пробелы. Остальное отклонять.
Форматировать без искусственного округления, нормализуя только `-0`.

**Rationale:** покрывает согласованные примеры, не добавляет функции,
переменные и новую систему точности. `2i` — специальная запись коэффициента,
а не включение общего неявного умножения.

**Alternatives considered:** только `2*i` проще, но расходится с выбранными
комплексными примерами; общее неявное умножение усложняет неоднозначности.
Округление до фиксированного числа знаков скрывало бы малые компоненты.

## R5. Ошибки и граница UI

**Decision:** дискриминированный объект успеха/ошибки, пять кодов,
сообщение и полуоткрытый span UTF-16. Фасад ловит только доменные ошибки.

**Rationale:** будущий UI сможет показать результат или выделить ошибку
без знания внутреннего AST; JS-индексы совпадают с операциями над строками
клиента. Синтаксис проверяется целиком до вычисления.

**Alternatives considered:** наружные исключения усложняют одинаковую
обработку UI и истории; одна строка ошибки не даёт стабильного кода
и позиции; возврат `NaN` нарушает пригодность к JSON-сохранению.

## R6. История и Undo

**Decision:** оставить вне реализации первой части, но зафиксировать
будущую запись `{expression, value}`, порядок добавления и удаление одной
последней успешной записи. Ошибочные вычисления историю не изменяют.

**Rationale:** сохраняет этапность и не добавляет файловые побочные эффекты
в чистое вычисление. История хранит исходный ввод и числовой результат,
а не форматированный текст или AST.

**Alternatives considered:** обратная арифметическая операция для Undo
не восстанавливает историю; запись ошибочных вычислений меняла бы
согласованную цель Undo. Расположение файла и I/O API отложены до следующего
этапа и не мешают реализовать текущий контракт.
